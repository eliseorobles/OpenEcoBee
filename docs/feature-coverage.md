# Thermostat feature coverage

Coverage snapshot: October 17, 2026. OpenEcoBee does not yet provide every feature available in the ecobee app. Use `get_capabilities` to inspect the running server's tool catalog and stated gaps before requesting a change.

An implemented adapter means the repository contains a fixed, validated operation. It does not establish that every model supports it or that it has been tested against a real thermostat. Device responses, configured permissions, and readback determine the result. Unsupported operations fail without substituting a different setting.

| Area | Implemented interface | Verification and limits |
| --- | --- | --- |
| Current thermostat state | `list_thermostats`, `get_thermostat_status`, `get_equipment_status` | Real thermostat reads have been verified. A setpoint is a target, not proof that the room has reached it or that equipment is running. |
| Temperatures and HVAC mode | `set_temperature`, `set_temperature_until`, `set_hvac_mode`, `resume_schedule`, `resume_all_events` | A real change to Cool mode and a 65 °F indefinite cooling hold have been verified with fresh readback. Holds support 1–24 hours, until changed, the next scheduled transition, or an explicit end date/time in the thermostat's local timezone. For an end-time hold, omit both start fields to begin now, or supply both for a scheduled start. Temperature-tool verification covers setpoints; use `get_events` to inspect hold duration. The heat/cool minimum gap applies in Auto mode. An all-event resume does not delete vacations. |
| eco+ master setting | `get_energy_status`, `set_eco_plus` | The master write has concrete upstream maintainer implementation evidence. The adapter requires the thermostat to expose the recognized `enabled`/`disabled` master states and checks readback. A live master-setting change has not been verified. |
| Individual eco+ features | Read whatever `get_energy_status` reports | Humidity adjustment, Time of Use, Schedule Assistant, savings levels, Pause When Open, and temporary "End eco+ for today" controls do not have verified write interfaces in this adapter. Reported Energy strings are preserved without inventing enum meanings. |
| Comfort Settings and schedules | `get_comfort_settings`, `get_schedule`, `set_comfort_setting`, `create_comfort_setting`, `update_comfort_setting`, `delete_comfort_setting`, `set_schedule` | Reads verified through ChatGPT; live changes unverified. Existing references are preserved, and ecobee assigns a reference to a new profile. Built-in profiles and custom profiles referenced by the schedule cannot be deleted. Updating a profile affects every activity using it. Weekly replacement requires seven Sunday-first days of 48 half-hour cells. |
| Fan | `set_fan`, `set_fan_speed`, documented fan settings through `update_settings` | Adapter implemented; live changes unverified. Fan holds use `auto`/`on` and an explicit duration. Fan speed is a separate persistent preference, limited to the thermostat's advertised wired capabilities. The supported two-speed mapping is handled separately from the displayed logical speed. |
| Settings and automation | `get_settings`, `update_settings`, `set_smart_recovery`, `set_demand_response_preference` | Settings reads verified through ChatGPT. Only the catalog's explicit writable-field allowlist is accepted. Advanced HVAC fields require `allow_advanced_settings=true`; hardware support still applies. Demand-response preference controls future acceptance behavior, not utility enrollment or cancellation of an active event. Legacy `autoAway` and `followMeComfort` settings do not prove control of every eco+ feature. |
| Sensors | `get_sensors`, sensor participation in `update_comfort_setting`, `rename_sensor` | Adapter implemented; live changes unverified. References must belong to the selected thermostat. Sensor rename requires compatible sensor metadata. |
| Vacations | `get_vacations`, `create_vacation`, `delete_vacation` | Adapter implemented; live changes unverified. Uses explicit temperatures and thermostat-local dates/times. Deletion targets the exact existing vacation name. |
| Alerts, reminders, and messages | `get_alerts`, `get_notification_settings`, `update_notification_settings`, `acknowledge_alert`, `send_message` | Alert reads verified through ChatGPT; live changes unverified. Reminder updates target device-reported types, preserve unrelated configuration, and validate filter intervals and paired limits. Computed reminder dates and notification recipients cannot be changed. Alert acknowledgement targets a returned reference. Messages display on the thermostat; they do not send email, SMS, or chat messages. |
| Additional data | `get_thermostat_details`, `get_events`, `get_weather`, `get_runtime_report`, `get_extended_runtime`, `get_groups`, `get_house_details`, `get_utility_info`, `get_technician_info` | Subject to the selected section, portal method, and device availability. Runtime reports are bounded to 31 inclusive days. Sensitive household and contact sections require explicit selection. |
| House characteristics | `update_house_details` | Adapter implemented; live changes unverified. Only supplied supported characteristics are changed. Window-efficiency information can affect frost-control behavior. |
| Thermostat name | `rename_thermostat` | Adapter implemented; live changes unverified. Follows the public portal's 20-character name limit. |
| Audio | `update_audio` | Adapter implemented; live changes unverified. Supports reported playback volume, microphone enablement, alert volume, and key-press volume fields. Requires compatible audio data from the device; voice-engine grants are not changed. |
| Timezone and daylight saving | `set_timezone` | Adapter implemented; live changes unverified. Changes the reported Olson/IANA timezone and/or daylight-saving preference. The UTC offset remains read-only. Address and contact information are not part of this tool. |
| Installer-code requirement | `set_installer_code_required` | Explicitly changes the local code-required preference. It does not read or change an actual code. Live change unverified. |
| Thermostat groups | `get_groups`, `create_group`, `update_group`, `delete_group` | Adapter implemented; live changes unverified. Operations preserve the full current collection and unrelated groups. Updates preserve omitted membership and flags; a membership change requires the explicit full member list. Creation requires explicit owned members, and deletion requires `confirm_delete=true`. Every affected member must belong to the signed-in account. Implicit moves from another group are rejected. Synchronization can propagate future changes across thermostats. |
| Preference reset | `reset_preferences` | Requires an explicit reset request and `confirm_reset=true`. Resets user preferences and the program, retaining installer/Wi-Fi configuration. Live reset unverified; it is not a routine reconnection or troubleshooting step. |
| Utility enrollment and account security | No account-management tools | Enrollment, withdrawal, credentials, actual access-code values, linked-app grants, and account-security settings are outside this interface. |

Thermostat energy, settings, comfort-profile, sensor, weather, and alert reads have been exercised through a real ChatGPT MCP connection. This does not verify every returned subsection or any unrelated write.

## Remaining public-API gaps

The catalog contains 46 extended thermostat operations plus six core/catalog tools, for 52 tools total. It does not expose every documented ecobee operation. The following need separate implementation and verification; an existing generic settings tool does not imply they work:

- Changing thermostat location addresses or contact information. `set_timezone` supports only the [timezone and daylight-saving fields](https://www.ecobee.com/home/developer/api/documentation/v1/objects/Location.shtml).
- Individual eco+ toggles, savings preferences, and ending eco+ for the day; the evidence and limitations are detailed below.

Some gaps are device or account restrictions. The [Device object](https://developer.ecobee.com/home/developer/api/documentation/v1/objects/Device.shtml) is read-only remotely; physical thermostat setup is required for changes. [`SetOccupied`](https://www.ecobee.com/home/developer/api/documentation/v1/functions/SetOccupied.shtml) is EMS-only and errors on consumer Smart thermostats. [`ControlPlug`](https://www.ecobee.com/home/developer/api/documentation/v1/functions/ControlPlug.shtml) requires a supported attached plug; its existence in the API does not establish support on a modern thermostat. Security-sensitive voice-assistant unlinking is also outside the current thermostat-control catalog.

Audio writes follow the documented [Audio object](https://www.ecobee.com/home/developer/api/documentation/v1/objects/Audio.shtml): playback volume is 0–100, alert/key-press volume is 0–10, and microphone enablement is Boolean. These controls require the corresponding field in a fresh device response. Fan-speed writes follow the maintained [Ecobee Suite implementation](https://github.com/SANdood/Ecobee-Suite/blob/6dc0d587519303900304aa6a5d8cd9bf6aa936d6/devicetypes/sandood/ecobee-suite-thermostat.src/ecobee-suite-thermostat.groovy#L2336-L2345), which treats fan speed as a persistent setting and handles the advertised two-speed HIGH/MEDIUM wire-value distinction. These are source-verified paths, not live device tests.

[Group updates](https://www.ecobee.com/home/developer/api/documentation/v1/operations/post-group-update.shtml) use the full fresh collection, following the [public portal's save/delete implementation](https://www.ecobee.com/consumerportal/scripts/ecobee.components.7d351bac.js). The [Group reference](https://www.ecobee.com/home/developer/api/documentation/v1/objects/Group.shtml) also warns that omitted members can delete a group and omitted synchronization flags default to false. OpenEcoBee reads and validates every affected member before changing the requested group; it does not substitute an unrestricted group proxy.

## What is known about the eco+ interface

Ecobee officially documents [`Selection.includeEnergy`](https://www.ecobee.com/home/developer/api/documentation/v1/objects/Selection.shtml), which requests energy configuration. The official [`Runtime` documentation](https://www.ecobee.com/home/developer/api/documentation/v1/objects/Runtime.shtml) also explains that `actualTemperature` can be a humidity-adjusted "feels like" value when `Energy.FeelsLikeMode` is `humidex`; `rawTemperature` is the dry-bulb reading. These references establish read behavior, not a complete writable Energy schema.

The maintained Go client models `energyFeatureState`, `feelsLikeMode`, `comfortPreferences`, and `tou` as strings and explicitly describes the [Energy object](https://github.com/sherif-fanous/go-ecobee/blob/5c1dba5d1b4c9d77c0c240c385f546be5fec182e/objects/energy.go) and [TimeOfUse object](https://github.com/sherif-fanous/go-ecobee/blob/5c1dba5d1b4c9d77c0c240c385f546be5fec182e/objects/timeofuse.go) as undocumented. Those models do not provide validated feature-specific setters or complete enum values.

The UDI maintainer's cloud backend provides stronger evidence for the master control: [`cmdSetECO`](https://github.com/UniversalDevicesInc-PG3/udi-poly-ecobee/blob/ecb95c4acd2059e93fc6b96ff443bc87a0f6fbf9/nodes/backends/cloud/Thermostat.py#L781-L805) sends `thermostat.energy.energyFeatureState` using `enabled` or `disabled`. Its [`ecobeePost` transport](https://github.com/UniversalDevicesInc-PG3/udi-poly-ecobee/blob/ecb95c4acd2059e93fc6b96ff443bc87a0f6fbf9/nodes/backends/cloud/Controller.py#L918-L944) adds the selected thermostat and posts to `1/thermostat`, checking the API status. The project records ECO+ control in its [version 3.1.3 changelog](https://github.com/UniversalDevicesInc-PG3/udi-poly-ecobee/blob/ecb95c4acd2059e93fc6b96ff443bc87a0f6fbf9/CHANGELOG.md). This is upstream implementation evidence, not an ecobee guarantee or proof of a successful write from OpenEcoBee.

No verified setter and complete enum mapping was found for `feelsLikeMode`, `comfortPreferences`, `tou.featureState`, or `tou.savings` in the reviewed official references and primary maintainer sources. OpenEcoBee therefore does not infer these writes from similarly named read fields. Ecobee's documented [eco+ app controls](https://support.ecobee.com/s/articles/eco-Frequently-Asked-Questions) remain available to users; this does not imply that an underlying callable interface is impossible.

## Holds and energy features

An [indefinite manual hold](https://support.ecobee.com/s/articles/What-s-the-Hold-setting-on-my-ecobee-thermostat-and-how-do-I-use-it) overrides the normal schedule and uses Home Comfort Setting sensor participation. [Smart Recovery / Pre-Cool](https://support.ecobee.com/s/articles/pre-heat-and-pre-cool-settings) does not run during an indefinite hold. The dedicated tool accepts positive `heat_enabled`/`cool_enabled` preferences and translates them to ecobee's inverted `disablePreHeating`/`disablePreCooling` fields, as verified in the public portal UI. Changing those preferences does not cancel a hold. An indefinite hold is not evidence that every eco+ feature is disabled or that the displayed temperature is a dry-bulb reading.

Community Energy Savings behavior depends on the program. The [utility-program article](https://support.ecobee.com/s/articles/eco-features-Community-Energy-Savings) describes utility contact for permanent withdrawal; the [newer program FAQ](https://support.ecobee.com/s/articles/eco-Community-Energy-Savings-Program-FAQ) describes an app toggle for its announced rollout. The master eco+ tool does not enroll or withdraw an account from either program. The official [SetHold reference](https://www.ecobee.com/home/developer/api/documentation/v1/functions/SetHold.shtml) warns that a hold created during active demand response inherits the event's end time; OpenEcoBee blocks temperature and HVAC changes when it detects an active demand-response event.

## Extending coverage

For a missing operation, first establish the exact supported method, payload, enum values, device restrictions, and possible side effects from current first-party behavior or a maintained implementation. Add bounded inputs and ownership checks, verify the adapter without changing unrelated state, then perform a deliberately authorized live check with readback. Update this document with the observed result. Never label a control supported solely because a read field or app toggle has a similar name.
